# 为什么把同步快照存进同步目录

## 背景

文件同步采用三方合并: 上一次同步成功后的状态作为基线, 与两端当前状态比较, 判断哪一侧发生了新增, 修改或删除.

在旧实现中, 每对同步关系只有一份基线, 保存在本项目的 `data/sync_pairs/<pair>/pair_state.json` 里. 它记录的是"主控设备执行上一次同步时看到的状态".

## 问题

基线实际上描述了"被同步的文件夹在上一次同步后的状态", 却寄生在"执行同步的那台机器"上. 一旦换一台机器做主控, 新的主控端既读不到旧基线, 也无法判断对端在多台设备之间是否已经变化.

## 场景

1. 在家里, 用 macOS 上的 FileSyncProApp 完成 `macOS:foo` 与 `Android:foo` 的同步. 此时 Android 端已经持有双方一致的内容.
2. 来到公司, 用 Windows 上安装的 FileSyncProApp 完成 `Windows:foo` 与 `Android:foo` 的同步.

在旧实现中, 第二步做不到平滑衔接: 因为 Android 端的基线保存在家里的 macOS 上, Windows 端拿不到, 只能把这次同步当作"首次同步", 重新建立基线; 双方历史差异会被误判为大量新增或冲突.

## 设计决定

把快照文件存进同步目录自身:

- 每一侧各自保存一份快照, 路径为 `<sync root>/.file_sync_shot.json`.
- 快照只记录相对路径及其 `kind`, `size`, `mtime`, `hash`, `textHash`, 不包含绝对路径或设备身份. 因此它可以随文件夹一起被复制, 迁移.
- Planner 同时接收两侧快照 (`baseA`, `baseB`), 每一侧只与自己的快照比较: A 是否变化看 `baseA`, B 是否变化看 `baseB`.
- 每次同步成功后, 分别把两侧的扫描结果写回各自的快照. 对未解决的冲突, 保留该侧快照里的旧条目, 让冲突持续可见.
- 快照文件名加入默认忽略规则, 不参与同步, 也不会进入对端 manifest.

这样一来, 第 2 步中的 Windows 端可以直接读取 Android 端目录里的快照, 判断 Android 自上次同步后是否发生变化; Windows 自己第一次同步时没有快照, 按"首次同步"处理, 但不会再打扰 Android 既有的基线.

## 兼容与迁移

- 旧版本的 `pair_state.json` 只作为只读回退: 当两侧都没有快照, 且记录中的 `rootA` / `rootB` 与当前配对一致时, 使用一次旧基线.
- 下一次同步成功后, 快照写入两侧目录, 后续不再依赖旧状态文件. 旧文件不会被自动删除, 以免误删用户数据.
- 新版配置与旧版兼容: 快照是运行时数据, 不改变 `sync.config.json` 的结构.

## 取舍与边界

- **并发**: 如果两台主控设备同时与同一目录同步, 可能出现快照互相覆盖. 当前策略是"最后写入者获胜", 后续可以加入版本号或目录级锁.
- **快照可能被删除**: 用户或第三方清理工具可能删掉隐藏文件. 缺失快照等价于首次同步, 系统会自动重建, 但会重新经历一次全量比对.
- **隐藏文件并非隐形**: 部分备份或同步工具会处理点文件, 需要把 `.file_sync_shot.json` 加入它们的忽略列表.
- **职责范围**: 本次只迁移基线快照. 同步日志与冲突备份仍然留在 `stateDir`, 因为它们属于诊断数据, 不随文件夹迁移.

## 结论

快照从"工具状态"变成了"文件夹状态". 同步工具因此与快照管理解耦, 任意一台设备都能接手同一对文件夹的后续同步.
