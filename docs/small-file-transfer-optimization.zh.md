# 小文件传输优化

本文讨论同步过程中"大量小文件"造成的性能瓶颈, 以及可行的优化方案. 当前只落地了方案 A (有界并发), 其余方案保留作为后续选项.

## 1. 现象与成本模型

同步的传输阶段由 `PlanApplier` 驱动, 原实现是单连接串行: 一个文件读完 + 写完并校验后, 才开始下一个文件.

每个文件都有与大小无关的固定成本:

1. 一次 HTTP 请求 + 一次响应, 至少 1-2 个 RTT.
2. 服务端创建临时文件, 写入, rename (原子替换).
3. 客户端写入后再发一次 `stat` 做大小校验.
4. 快照记账与 UI 回调.

按 LAN RTT 1-3ms 估算, 单个小文件的固定开销约 5-8ms. 1000 个文件就是 5-8 秒, 即使总字节数很小. 串行执行时这些延迟完全没有重叠, 吞吐约等于 `文件数 / 单文件往返时间`, 与链路带宽无关.

图库里的照片多为 2-5MB 的"中文件", 传输时间开始占主导, 但固定成本仍占 1%-10%. `收集` 目录约 4GB / 637 个文件, 平均 6.3MB, 是典型的混合场景.

参考数据:

| 场景 | 实测 / 估算 |
|---|---|
| 公司 LAN (当前) | 约 10MB/s |
| 手机 Wi-Fi 6 5GHz 热点 (80MHz, 2x2) | 现实 37-75MB/s |
| 本机扫描 1000 级文件 | 约 1.3s |
| 手机扫描同规模文件 | 约 6.7s |

## 2. 方案

### 方案 A: 有界并发 (已实现)

用固定数量的 lane 同时拷贝多个文件, 把每个文件的往返延迟重叠起来.

- **并发度**: 4 条 lane.
- **大小分流**: `< 8MB` 的文件走并发 lane; `>= 8MB` 的文件单独一条 lane, 一次只跑一个.
- **顺序**: 所有待写文件按大小降序排列, 大文件先起跑, 小文件填补剩余带宽, 避免一个几十秒的大文件排在几百个小文件后面.
- **失败语义**: 任一文件失败后不再派发新任务, 但会等待所有在途拷贝结束, 再抛出第一个错误, 保证不会留下悬空的写入.
- **取消**: 复用现有的 `SyncCancelToken`, 每个 lane 在取任务前和每个数据块之间检查.

为什么不是越大越好: 对端文件服务器是单 isolate, 并发请求最终仍在同一个事件循环里处理; lane 太多只会增加内存和在途临时文件, 不会提高吞吐. 对带宽受限的链路, 并发也不能突破总带宽.

### 方案 B: 多文件打包成一条流

把 N 个小文件装进一个 HTTP 请求 (自定义分帧: 路径长度 + 路径 + 大小 + 字节, 或 multipart), 服务端逐个落临时文件, 全部完成后统一 rename.

- **收益**: 把 RTT 和 HTTP 头开销摊薄, 对 `< 256KB` 的文件可提升一个数量级.
- **代价**: 协议要升版, 两端同时改; 需要重新定义"一批里某个文件失败"的部分成功语义, 进度粒度也会变粗; 断点续传和取消要按批处理.
- **适用**: 代码仓库, 图标, 缩略图等海量微小文件. 对 2-5MB 的照片收益有限, 因为传输时间本来就占主导.

### 方案 C: 压缩

- 照片和视频本身已压缩, 再压是浪费 CPU.
- 只有文本类小文件能压 3-5 倍, 适合作为打包流里的可选开关, 不建议单独实现.

### 方案 D: 流水线重叠

不并发, 但让"读下一个文件"和"写当前文件"重叠 1-2 个.

- 实现量比 A 小, 收益约为 2 倍, 天花板低于 A.
- 可以作为低配实现, 但 A 已经覆盖了它的收益.

### 方案 E: 零散优化

- HTTP 客户端已经复用连接 (`HttpClient` 常驻), 不需要每次握手.
- 每次写入后的 `stat` 校验可以合并进 PUT 的响应, 省掉一次 RTT.
- 大文件的分块可以加大到 256KB-1MB, 减少流控开销.
- 扫描阶段的哈希仍是手机端的主要耗时, 依赖哈希缓存与采样指纹, 与传输优化无关.

## 3. 选型结论

只做方案 A:

- 改动局限在 `PlanApplier`, 不碰线协议, 风险低.
- 对"文件多, 单个不大"的图库场景收益直接.
- 方案 B 的复杂度 (协议版本, 部分失败语义, 进度与取消) 与当前收益不匹配, 等 A 实测后再评估.

## 4. 实现要点

代码位置: `lib/features/sync/application/plan_applier.dart`.

- `_parallelThresholdBytes = 8MB`, `_parallelLanes = 4`.
- 写入列表按 `entry.size` 降序排序后拆成两组, 分别交给 `_runPool`.
- `_runPool` 是一个通用的有界任务池: 先取任务再 await, 单 isolate 下 `next++` 无需加锁; 失败后停止派发并等待在途任务.
- `created` / `updated` / `written` 在单 isolate 内并发写是安全的; 进度回调仍然每完成一个文件触发一次.
- 目录创建仍然先于文件写入按深度升序执行, 文件删除仍然在写入之后串行执行, 删除与目录清理的顺序语义不变.

## 5. 验证

单元测试 (`test/features/sync/plan_applier_test.dart`):

- 8 个 4KB 文件 -> 观测到 4 条 lane 同时在写.
- 2 个 9MB 文件 -> 观测到同一时刻只有 1 个在写.
- 取消测试 (`local_sync_test.dart`) 改为 10 个文件, 保证停止时仍有排队任务: 已完成的文件保留, 无 `.filesync-` 残留, 快照不更新, 下一次运行重新规划全部文件.

实测计划 (手机热点):

1. 关闭手机 Wi-Fi, 打开 5GHz 热点.
2. 电脑连接热点, 更新设备地址为热点网关.
3. 刷新两侧快照, 同步 `收集` 目录 (约 4GB / 637 个文件).
4. 记录总耗时与平均速率, 与公司 LAN 的约 10MB/s 对比.

## 6. 后续观察点

- 若耗时仍由小文件主导, 说明 per-file 固定成本没有被并发完全掩盖, 再考虑方案 B.
- 若大文件明显拖慢整体, 可以调低阈值, 让更多"中文件"进入并发 lane.
- 若链路成为唯一瓶颈 (热点实测接近 75MB/s), 并发度可以降到 2-3, 减少手机端临时文件与内存占用.
